# Changelog

## [1.1.1] - 2026-10-31

### Added
- **The One Probe: valve open/closed state.** Pointing at any of the three valves now shows `Valve: Open` / `Valve: Closed` (green/red) plus the configured input and output faces. The provider is a plain `IProbeInfoProvider` registered from `SuTopIntegration` (only when `theoneprobe` is installed) and localises through TOP's `{*key*}` markers. Docs: [docs/redstone_valves.md](docs/redstone_valves.md) §8.1.
- **Three redstone-controlled valves** (single-block MTEs, no GUI, no buffer, no maintenance):
  - `susyplusplus:fluid_valve` (MTE id **32123**) — fluid pass-through;
  - `susyplusplus:logistics_valve` (**32124**) — item pass-through;
  - `susyplusplus:ir_fluid_valve` (**32125**) — fluid pass-through **plus** active extraction at `Integer.MAX_VALUE` per tick (Industrial Renewal parity).
  Behaviour: open with no redstone signal, closed while powered; **wrench = set input face, Shift+Wrench = set output face** (the two faces stay distinct — they swap if you pick the other one). Both faces always expose a non-null `IFluidHandler` / `IItemHandler`, so **pipes stay connected while the valve is closed** (this pack runs `gt6StylePipesCables=true`, where pipe connections are never recomputed from capabilities); the closed side simply refuses to accept anything. New config option `enableRedstoneValves` (default `true`), assembler recipes (circuits 14/15/16), and docs in [docs/redstone_valves.md](docs/redstone_valves.md).
- **Steam Pump cover** (`susyplusplus:steam_pump`, config `enableSteamPump`, default `true`): a `CoverPump` subclass that moves **1024 L/t** (20,480 L/s), **steam only** (exact-name whitelist `gregtech:steam` / `susy:dense_steam`), **no EU, no buffer**, reusing GT's LV pump texture. `CoverPump`'s rate is a *per-second quota* that a single tick may spend all at once, so the cover also clamps `doTransferFluids(int)` to 1024 per tick. Its fluid filter is layered **on top of** the steam whitelist (2.8.7 has no `createFilterRow()` hook to hide it). Assembler recipe: circuit 17 + LV electric pump + 4 steel plates + redstone. Docs: [docs/steam_pump_and_pipes.md](docs/steam_pump_and_pipes.md).
- **Steam pipes: 2 pressure classes × 5 sizes = 10 blocks** (`susyplusplus:low_pressure_steam_pipe_{tiny,small,normal,large,huge}` and `high_pressure_...`), steam-only, built on GT's `BlockPipe` (so pipe connections, wrench face blocking, the 3×3 face grid, covers and collision boxes behave like GT pipes). Rate follows the user's rule "base rate = tiny, multipliers = GT fluid pipes (×1/×2/×6/×12/×24)": low pressure 64 / 128 / 384 / 768 / 1536 L/t, high pressure 256 / 512 / 1536 / 3072 / 6144 L/t. Transport is the **same "instant whole-network distribution" model as GT fluid pipes**: the pipe stores nothing; a `fill` BFS-walks the same-pressure network and fills the end-point handlers (machines, tanks, **GT fluid pipes**) directly, a `drain` pulls from those end points, and the flow is capped by the **thinnest** pipe in the run. Low-pressure and high-pressure pipes never connect (the check lives in `canPipeConnectToBlock`, because the 10 sizes are 10 different blocks and GT routes "different block" neighbours through that method); different sizes of the same pressure do. Rendering reuses GT's pipe sprites (`PIPE_TINY…HUGE` + `PIPE_SIDE`) through a small custom `PipeRenderer` (colour-coded: low = orange, high = black), because `FluidPipeRenderer` requires a `Material`. Crafting follows GT's own pipe material amounts (`pipeTinyFluid = M/2` … `pipeHugeFluid = 12M`): **alloy smelter** (`ALLOY_SMELTER_RECIPES`, which is also the recipe map of GT's `SteamAlloySmelter`, so it is steam-age craftable), **potin (rough bronze alloy) for low pressure / steel for high pressure**, and a **different shape mold per size** (`notConsumable`: nugget / ball / ingot / cylinder / block — 2.8.7 ships no pipe molds) so the five sizes cannot collide with each other or with GT recipes. Each item ([`ItemBlockSteamPipe`](src/main/java/com/susy/plusplus/pipe/steam/ItemBlockSteamPipe.java)) shows its **rate (L/t)**, pressure level and "steam only" as a tooltip, and holding any pipe item splits the pipe collision box into GT's **3×3 face grid**. Docs: [docs/steam_pump_and_pipes.md](docs/steam_pump_and_pipes.md).

### Removed
- **Multiblock tanks and tank valves deleted.** Susy-Core 2.0 ships its own multiblock tanks, so this mod no longer registers duplicates: `susyplusplus:clean_stainless_steel_multiblock_tank` (MTE id 32111), `susyplusplus:reinforced_titanium_multiblock_tank` (32113), `susyplusplus:clean_stainless_steel_tank_valve` (32116) and `susyplusplus:reinforced_titanium_tank_valve` (32118) — plus their two classes (`SuMultiblockTank`, `SuTankValve`), four shaped recipes, language keys and the unused `SuStorageTier` tank-capacity field — are gone. **Existing worlds:** controllers / valves of the removed types will be dropped as unknown MTE items; move their fluids out before updating.

### Changed
- **Multiblock crate capacity ×4**: steel **4,000,000** items, clean stainless steel **64,000,000**, reinforced titanium **128,000,000** (was 1M / 16M / 32M). The `VirtualItemStorage` counter is already a `long`, so no storage-format change is needed.
- Docs updated accordingly ([docs/multiblock_crate_and_tank_upgrades.md](docs/multiblock_crate_and_tank_upgrades.md), `docs/config.md`, `README.md`).

### Added
- **Configurator mode 5: rename a placed machine.** Rename the Configurator in an anvil, select "Rename machine", then plain right-click any placed GT machine — the name is written to the block entity's `CustomName` (exactly what an anvil-renamed machine gets on placement) and pushed to clients immediately via `notifyBlockUpdate`, so the floating name tag appears at once. Right-clicking with an **unnamed** configurator clears the name. Implemented through `MachineNameHelper` (reflection over `MetaTileEntityHolder#setCustomName`, so no hard AE2 dependency), and `ConfiguratorMode#write` now preserves the anvil `display` tag when switching modes. Docs: [docs/configurator.md](docs/configurator.md).
- **Chinese translations for Susy-Core 2.0 content that ships untranslated**, now **disabled by default** (`enableSusyTranslations`, default `false`). Minecraft loads every `assets/<modid>/lang/<locale>.lang` unconditionally, so the file was moved out of `lang/` to `assets/susyplusplus/lang_override/susy_zh_cn.lang`; when the option is enabled, `SusyLangOverride` (an `IResourceManagerReloadListener`) reads it and injects the key/value pairs into the client `Language`'s internal map via reflection (field located **by type**, so it works both in dev (`languageList`) and in production (`field_74805_a`)). It only adds keys — Susy-Core's own translations are never replaced — and a reflection failure logs a warning instead of crashing. Docs: [docs/steam_pump_and_pipes.md](docs/steam_pump_and_pipes.md) §1.

- **Configurator mode 5 is now a real UI** ([`ConfiguratorRenameUI`](src/main/java/com/susy/plusplus/gui/ConfiguratorRenameUI.java)): after selecting "Rename machine", right-clicking a machine opens a panel with a **name field** (pre-filled with the current name), **Apply**, **Clear name** (deletes the `CustomName` NBT entry) and **Close**. Writes go through `PacketRenameMachine` (server-authoritative, 8-block reach check) and the server answers with `PacketSyncMachineName`.
- **TOP shows the machine's custom name**: [`MachineNameInfoProvider`](src/main/java/com/susy/plusplus/integration/top/MachineNameInfoProvider.java) adds a gold `Name: <name>` line for any GT machine that has a `CustomName` (registered from `SuTopIntegration`).

### Fixed
- **`NoSuchMethodError` crashes when opening the Configurator UI / looking at a Steam Pipe / using the Trolley / spraying with the Waterproof can.** Root cause is the build toolchain, not logic: `getHeldItem(EnumHand)`, `getHeldItemMainhand()`, `getHeldItemOffhand()` are declared on `EntityLivingBase` and `isSneaking()` on `Entity`, and RFG's reobf **does not resolve mappings up the class hierarchy** — calls whose receiver was typed `EntityPlayer`/`EntityPlayerSP` were left with their MCP names and blew up at runtime (confirmed by eight crash reports). All such call sites now go through the new [`PlayerHeld`](src/main/java/com/susy/plusplus/util/PlayerHeld.java) helper, which casts the receiver to the declaring class (`EntityLivingBase` / `Entity`) so reobf maps them to `func_184614_ca` / `func_184592_cb` / `func_184586_b` / `func_70093_af`. Verified by disassembling the reobfuscated jar (no unmapped names remain).
- **Steam pipes could not connect or move fluid.** Two causes: (1) the crash above happened inside `BlockSteamPipe#isHoldingPipe`, which GT calls from `getCollisionBox`, so merely looking at a pipe crashed the game; (2) the first version only exposed an `IFluidHandler` on *already connected* faces, but GT's `canPipeConnectToBlock` decides connections by asking exactly that — a chicken-and-egg deadlock. Every face now exposes the handler unconditionally, and transport was rewritten from per-tick pushing to GT-style network distribution (no per-segment delay, no fluid left inside pipes).
- **Steam pipes were ~4× cheaper than GT's own pipes** (1 plate → 8 pipes). They are now alloy-smelter recipes with GT's own material amounts (tiny 1 ingot → 2, small 1 → 1, normal 3 → 1, large 6 → 1, huge 12 → 1), potin (rough bronze alloy) for low pressure and steel for high pressure.
- **`RuntimeException: TileEntitySteamPipe is missing a mapping!` whenever a steam pipe is placed (this is what "opening the Configurator UI still crashes" actually was).** The tile entity class had never been registered, and Minecraft resolves "class → registry name" while writing NBT / building chunk packets (GT's `BlockPipe` overrides `getUpdateTag`), so any chunk sync near a pipe threw inside `World.tick`. `SusyPlusPlus#preInit` now calls `GameRegistry.registerTileEntity(TileEntitySteamPipe.class, new ResourceLocation("susyplusplus", "steam_pipe"))`.

- **Renaming changed `CustomName` but the floating name tag kept the old text.** GT's `MetaTileEntityHolder#updateNameTagParticle()` only *creates* the name-tag particle when `nameTagParticle == null`; an existing particle is never refreshed (verified with javap on 2.8.7). The client now receives `PacketSyncMachineName` and `MachineNameHelper#applyNameOnClient` first writes an empty name (so GT recycles the old particle) and then writes the real name (so a new particle with the new text is created) — the tag updates immediately.

- **Chinese machine names turned into gibberish after renaming.** `PacketRenameMachine` / `PacketSyncMachineName` wrote `String.length()` (characters) but the reader treated it as a **byte** count; a Chinese character is 3 bytes in UTF-8, so the string was truncated mid-sequence. Both packets now write/read an explicit **UTF-8 byte array** (`length` = `bytes.length`, capped at 4× the character limit).

## [1.1.0] - 2026-10-02

### Changed
- **Electric Grinder redesigned: it no longer clones recipes — it reuses GT's `MACERATOR_RECIPES` directly** (`super(metaTileEntityId, RecipeMaps.MACERATOR_RECIPES)`). Yield, byproducts and duration are now literally the macerator's own recipe objects (no field-copy drift possible), any GroovyScript change to the macerator is followed automatically with **no timing problem at all**, and JEI shows the standard **Macerator** category instead of a separate `electric_grinder` map. All the machinery written while trying to clone — the own `RecipeMap`, the three-pass clone with input claiming, the `@Pseudo` mixin on GroovyScript `runGroovyScriptsInLoader`, and the load-complete hook — has been **deleted**; why each of them could not work is documented in [docs/electric_grinder.md](docs/electric_grinder.md) §1.3. *(The `### Added` / `### Fixed` bullets below describe the now-removed clone approach and are kept for history.)*
- **Electric Grinder parallel is now a hard-coded 32 and the config option is gone.** The previous `electricGrinderParallel` option looked like it had no effect because **Forge never updates a config entry that already exists**: a `run/config/susyplusplus.cfg` written by an older build kept `I:electricGrinderParallel=16` (verified in the actual file), so changing the code default did nothing. The option has been removed entirely — the machine always uses `MetaTileEntityElectricGrinder.PARALLEL_LIMIT = 32`, and the now-unknown key disappears when Forge rewrites the config.
- **Electric Grinder structure rewritten as a symmetric 3×3×3 shell** (uniform steel casing + four steel-frame corner columns, controller in the middle of one face) instead of the previous asymmetric "feed hopper in front / gearbox behind" 3×3×5 layout. Reason: GT's JEI preview draws the pattern in a fixed orientation while the placed machine's pattern is *rotated* according to the controller's `frontFacing`, so an asymmetric pattern makes the built structure look 90°/180° off from the preview. A symmetric shell (the same approach as `MetaTileEntityReinforcedPBF`) can be rotated freely, so the preview and the placed machine always agree.
- **Electric Grinder tooltip trimmed to three short lines** (`32 parallels` / `same recipes as the Macerator` / `no maintenance`) and its now-stale keys (`recipemap.electric_grinder.name`, `block.susyplusplus.electric_grinder`) are marked unused.

### Added
- **Battery Case: configurable slot count** (`batteryCaseSlots`, default `4`, range 2–16, snapped to **2 / 4 / 8 / 16**). The UI lay-out follows the chosen size (2 slots = 1 row, 4 = 2×2, 8 = 2 rows of 4, 16 = 4×4), and the tooltip's "x / y" readout uses the case's real slot count instead of a hard-coded constant. The slot count lives in each case's own NBT, so a case is never shrunk on load — an existing case only gets *more* slots (the extra ones empty) if the config is raised, which means no batteries can be lost. ([`BatteryCaseInventory`](src/main/java/com/susy/plusplus/item/battery/BatteryCaseInventory.java), [`BatteryCaseBehaviour`](src/main/java/com/susy/plusplus/item/battery/BatteryCaseBehaviour.java))
- **Battery Case: optional nesting** (`batteryCaseNesting`, default `false` = the previous behaviour). When enabled, a Battery Case can be put inside another one; a nested case reports `canProvideChargeExternally() == true`, so it counts as a battery and its whole charge is aggregated into the outer case (and charged/discharged in slot order like any other battery). Putting a case inside **itself** is always rejected, since that would be a self-reference that recurses forever when serialised.
- **Electric Grinder** (`susyplusplus:electric_grinder`, MTE id **32103**) — an **LV electric ore-grinding multiblock** that fills the gap between the steam-era **Steam Grinder** and the MV-era **Eccentric Roll Crusher**. Docs: [docs/electric_grinder.md](docs/electric_grinder.md).
  - **The gap it fills**: the Steam Grinder runs **8 parallels with a ×1.5 duration penalty** (every steam multiblock goes through `SteamMultiWorkable` — SUSY's own `MetaTileEntitySuSyLargeHammer` confirms `PARALLEL_LIMIT = 8`), while the Eccentric Roll Crusher needs **MV plus manganese steel**. Manganese requires smelting `pyrolusite` in an ERF with a carbon source for a **75% chance** of a manganese dust, which is mid-to-late MV content. So until then, ore throughput never improved.
  - **A counter-intuitive finding that shaped the balance**: the Eccentric Roll Crusher is **not** a higher ore multiplier. Comparing the two source paths side by side (GT's `OreRecipeHandler#processOre` vs SUSY's `SusyOreRecipeHandler#processOre`), both emit `round(oreMultiplier) * 2 * oreTypeMultiplier` crushed ore. For overworld stone types the yields are **identical**; the Eccentric Roll Crusher's only edges are **50 vs 400 ticks** and **two 14%/850 byproduct rolls instead of one**. (Side note: because the two use different `oreTypeMultiplier` rules, `oreAnorthosite` actually yields **half** as much in the roll crusher — a SUSY quirk this mod does not touch.) Filling the gap with a *higher multiplier* would therefore have made the macerator obsolete and the roll crusher pointless, so this machine instead buys **throughput, not yield**.
  - **Identical yield, cloned rather than re-derived**: `ElectricGrinderRecipes` iterates `MACERATOR_RECIPES` and clones every "raw ore" recipe into the machine's own map, changing **only** `duration`. Inputs, outputs, chanced outputs and their chances are copied field-for-field, so a mismatch with the Steam Grinder is impossible, and any future GroovyScript edit to the macerator ore recipes is followed automatically. An `OrePrefix` processing handler could not be used: those run during material registration, long before this mod's postInit. (GT's `RecipeBuilder(Recipe, RecipeMap)` copy constructor is deliberately **not** used — see the traps bullet below.)
  - Ore recipes are recognised by two joint conditions: the input's `OreDictUnifier.getPrefix(...)` **name** starts with `ore` (an equality check against `OrePrefix.ore` would miss `oreGranite`, `oreMarble`, SUSY's `oreGabbro`, …), and at least one output is `OrePrefix.crushed`.
  - **16 parallels / 100 ticks** (the macerator ore recipe is 400). 16 is not arbitrary: the macerator recipe is `EUt = 2` and LV is 32 EU/t, so `32 / 2 = 16` is exactly GT's own voltage ceiling for parallel work. Steam Grinder is 600 tick ÷ 8 = **75 tick/item**; this machine is 100 tick ÷ 16 = **6.25 tick/item**, i.e. ≈ **12× the throughput** of the Steam Grinder and **64× a single-block LV macerator** — while yielding exactly the same items.
  - The machine deliberately **keeps one byproduct roll instead of two**, so the Eccentric Roll Crusher still has a reason to exist: wanting byproducts still means building one.
  - **Parallelism is delegated to GT**, not hand-rolled: a plain `setParallelLimit(...)`. GT's `ParallelLogic` caps actual parallelism by available inputs, output space and voltage simultaneously, so an over-full output bus lowers the parallel count instead of **voiding items**.
  - **No maintenance** (`hasMaintenanceMechanics() == false`, and `autoAbilities` is called with `checkMaintenance = false`, so the structure rejects maintenance hatches) — matching the Steam Grinder and keeping the early-LV player unblocked.
  - **Structure** 3×3×5, built entirely from existing GT blocks (**no new blocks, no new textures**): Solid Steel Machine Casing (body, replaceable by hatches), Steel Frame Box (the two **jaws**), Steel Pipe Casing (top **feed hopper**), Steel Gearbox Casing (rear **eccentric drive / flywheel**), with the controller facing the feed direction so it stays right-clickable. `MIN_CASING = 10` of 27 possible casing positions.
  - Assembler recipe (30 EU/t, 600 ticks) deliberately contains **no manganese steel and no MV components** — LV hull, 2× LV motor, 2× LV circuit, 8× steel plate, 2× steel frame, 4× steel gear, 16× steel screw, 2× steel rotor, 2000 mB lubricant — so it is reachable right after steel.
  - Uses its own `RecipeMap` (unlocalizedName `electric_grinder`, JEI category via `recipemap.electric_grinder.name`). Reusing `MACERATOR_RECIPES` would have **overwritten the macerator's own 400-tick ore recipes with the 100-tick clones**, buffing the Steam/LV macerator as a side effect.
  - **Two silent-failure traps in GT's recipe API were found and avoided during implementation** (both would have left the machine looking "empty in JEI" with no crash):
    1. **`maxOutputs` must be 4, not 2.** An ore recipe emits `crushedX` plus *several* chanced outputs — the 1400/850 byproduct **and one per `secondaryMaterial`** (overworld ores carry `Stone 6700/800`; with `allUniqueStoneTypes` the granite/marble/netherrack variants add more). `RecipeMap#postValidateRecipe` rejects a recipe whose `outputs + chancedOutputs` exceeds `maxOutputs` **silently** (GTLog error, recipe dropped). The map is therefore declared exactly like GT's macerator: `new RecipeMap<>("electric_grinder", 1, 4, 0, 0, new SimpleRecipeBuilder().duration(150).EUt(2), false)`.
    2. **GT's `RecipeBuilder(Recipe, RecipeMap)` copy constructor cannot be used for cross-map cloning.** It sets `this.recipeMap = recipeMap` but leaves `this.category = recipe.getRecipeCategory()`, i.e. the *macerator's* category, and `RecipeBuilder#validate()` then fails with "Cannot apply Category with incompatible RecipeMap" → every clone discarded. Since `RecipeBuilder` exposes **no `getCategory()`**, the clone is instead built from `target.recipeBuilder()` (whose sample already carries the correct `recipeMap` + `category`) with the source recipe's fields copied across using only verified overloads (`inputIngredients`, `outputs`, `chancedOutputs(List<ChancedItemOutput>)`, `fluidInputs`, `fluidOutputs`, `chancedFluidOutputs(List<ChancedFluidOutput>)`).
  - Because `buildAndRegister()` returns `void` and swallows validation failures, the loader **reads back `target.getRecipeList().size()`** after cloning and logs an ERROR if fewer recipes landed than were cloned, naming the likely cause. "Called buildAndRegister N times" is not evidence that N recipes registered.
  - Works in **pure GregTech** too — it depends on no SUSY machine or material, so unlike the Wireless Energy Tower / Fluid Sample Storage it is **not** disabled by `vanillaGtCompat`.
  - New config options `enableElectricGrinder` (default `true`) and `electricGrinderParallel` (default `16`, range 1–64).
  - `en_us` / `zh_cn` localisation and a full tooltip.
  
  ### Fixed
  - **Electric Grinder: a duplicated ore recipe that made bauxite show up as the *vanilla* ore.** The first implementation blind-copied every macerator ore recipe, which surfaced a latent pack bug. In this pack, bauxite is special-cased by GroovyScript (`run/groovy/prePostInit/OreDict.groovy`): the `oreBauxite` ore-dictionary entry is swapped from GT's own `gregtech:ore_bauxite_0` to SUSY's `susy:resource_block:0`, and the auto-generated macerator recipe is deleted with `macerator.removeByInput(2, [item('susy:resource_block')], null)` before a hand-written **×4** recipe is added in `postInit/mod/GregTech.groovy`. **That deletion silently fails**: `GTRecipeOreInput` caches the item array resolved on its first call, and its own comment warns that the returned items are *"not updated after its first call … not suitable for use while recipes are being processed and the OreDicts being modified"* — the cache still holds the vanilla bauxite ore, so an item-based match finds nothing. The macerator therefore ends up with **two** live bauxite recipes that sit in *different branches* of GT's ingredient tree (ore-dictionary input vs. fixed-item input) and therefore do not even raise a collision: GT's `oreBauxite → crushedBauxite ×2` and the pack's `susy:resource_block → crushedBauxite ×4`. Copying both made the grinder show two conflicting bauxite entries, one of them displaying the vanilla ore that the pack `yeet`s from JEI.
    - **Fix: three cloning passes with input claiming, so the more specific recipe always wins.** (1) macerator recipes whose input is a **fixed item** (= the pack's hand-written overrides, e.g. bauxite ×4) are cloned first and claim their input items; (2) the eccentric roll crusher's hand-written recipes; (3) the macerator's **ore-dictionary** ore recipes, skipping any whose candidate inputs are **all** already claimed. "Fixed item" is detected via `GTRecipeInput#isOreDict()` rather than by looking at ore-dictionary registrations, because GT's auto-generated ore recipes are always `GTRecipeOreInput` (`isOreDict() == true`) while GroovyScript's `item(...)`/`metaitem(...)` produce `GTRecipeItemInput` (`false`) — so deposit blocks, which *do* carry ore-dictionary names, are still classified correctly. Skipping requires **all** candidates to be claimed (an ore-dictionary entry usually spans several stone types, so a partially-covered one still has value).
    - Input stacks are now read **live** from `OreDictionary.getOres(OreDictionary.getOreName(input.getOreDict()), false)` instead of `GTRecipeOreInput#getInputStacks()`, for the same stale-cache reason: otherwise the *filter* could also see the vanilla ore. `getInputStacks()` is still used for fixed-item inputs, with a null guard (the base `GTRecipeInput` returns `null`).
  - **Electric Grinder: the JEI structure preview did not render most of the casing, and right-clicking a block showed no replaceable-block list.** Root cause: `states(getCasingState()).setMinGlobalLimited(MIN_CASING)` was used for the casing character. `TraceabilityPredicate#setMinGlobalLimited(int)` is implemented as `limited.addAll(common); common.clear(); …`, i.e. it **moves the predicate from `common` to `limited`**, and `BlockPattern#getPreview` only renders a block while that entry still has `previewCount`/`minGlobalCount` **quota** left — only `common` entries with `previewCount == -1` are rendered for *every* remaining position. With `setMinGlobalLimited(10)` the preview drew 10 casings plus one of each hatch and left the other ~14 casing positions completely empty (no block, no candidates, no base texture). The casing predicate now stays in `common` (no min/max), which is exactly how GT's own machines write it (`MetaTileEntityLargeMiner`, `MetaTileEntityDistillationTower`, `MetaTileEntityFusionReactor`, `MetaTileEntityLargeTurbine`, `MetaTileEntityFluidDrill`). Hatches are now declared with explicit `abilities(...)` (mirroring this mod's `MetaTileEntityReinforcedPBF`) — energy 1–3, item input ≤2, item output ≤2 — and the structure is still strict, since every casing position must be casing-or-allowed-hatch. `MIN_CASING` is gone.
  - **Electric Grinder: the pack's GroovyScript recipes were never picked up at all — the clone ran at the wrong moment.** The fixes above only help *if* the recipes are seen, and they were not: the log showed `macerator overrides 0/0, eccentric-roll-crusher manual 0/0`, i.e. the pack's bauxite ×4 recipe and every deposit-block recipe were absent, so bauxite only had GT's ×2 entry and the deposit blocks had nothing. Measured timestamps (`run/logs/`) explain why: this mod's postInit runs at **00:41:28**, GroovyScript only *starts* its `postInit` scripts at **00:41:50** (finishing at **00:43:08**), and `FMLLoadCompleteEvent` — the only later hook — is dispatched as `groovyscript → jei → … → gregtech → susyplusplus` at 00:43:08, i.e. **after** JEI's plugin registration has already copied the recipe lists into JEI's index (JEI is dispatched second; this mod only after `gregtech`).
    - **So postInit is too early, and `FMLLoadCompleteEvent` is too late for JEI.** Fix: a `@Pseudo` mixin ([`GroovyScriptRunScriptsMixin`](src/main/java/com/susy/plusplus/mixin/groovyscript/GroovyScriptRunScriptsMixin.java)) injects at the `RETURN` of `GroovyScript#runGroovyScriptsInLoader(LoadStage)` — the tail of "a script stage finished" — and re-generates the recipe map *there*, which lands exactly between GRS and JEI. Because Mixin targets the class by **string**, GroovyScript does not become a compile dependency; `@Pseudo` plus a `Loader.isModLoaded("groovyscript")` gate in `SuMixinPlugin` skips the patch entirely in packs without it.
    - `ElectricGrinderRecipes#init` is now idempotent: it compares a "source signature" (the recipe count of both source maps plus the identity hash of each one's last recipe) and only rebuilds when the sources actually changed. It is called from postInit (GT's original recipes), after every GRS stage (which adds the pack's recipes), and once more from `SusyPlusPlus#loadComplete` as a safety net for GRS-less packs and dedicated servers. An `isEmpty()` guard on the macerator map stops the earliest stages (e.g. GRS's `preInit`) from latching an empty result.
    - **Startup-crash trap (hit and fixed):** that safety net must be a `@Mod.EventHandler` method on the `@Mod` class — **not** `@Mod.EventBusSubscriber` + `@SubscribeEvent`. `FMLLoadCompleteEvent` is not a Forge `Event` (FML lifecycle events are dispatched through each mod's own event bus), so registering it with `AutomaticEventSubscriber` throws `IllegalArgumentException: … takes an argument that is not an Event class` during mod construction and the game dies half-way into startup.
    - **Documented trap:** the obvious alternative — subclassing `RecipeMap` and generating lazily from `getRecipesByCategory()`/`getRecipeList()` — **cannot compile in this project**. GT's `RecipeMap` carries class-level `@ZenClass`/`@ZenRegister` annotations and CraftTweaker/ZenScript is not on the compile classpath, so `extends RecipeMap` makes javac fail with `cannot access crafttweaker.annotations.ZenRegister`. Merely *using* `RecipeMap` as a type only produces warnings, which is why the trap is easy to miss (`javap -v` confirms the annotations sit on `RecipeMap` itself, not on `Recipe`/`GTRecipeCategory`).
  - **Electric Grinder: the eccentric roll crusher's hand-written recipes were missing.** ~13 recipes are added to `SuSyRecipeMaps.ECCENTRIC_ROLL_CRUSHER` by GroovyScript (deposit blocks → dust, e.g. `run/groovy/postInit/mod/GregTech.groovy:860` and the monazite / iodine / platinum-group / gold chains). Their inputs are concrete deposit blocks rather than `ore*` prefixed items, so the ore-prefix filter missed them all. They are now cloned **verbatim** — same outputs, **no extra byproduct, no yield multiplier change**, and their **original duration/energy kept** (30 ticks / ULV, unlike the 100-tick macerator clones). The recipe map is looked up **by name** with `RecipeMap.getByName("eccentric_roll_crusher")` instead of referencing `supersymmetry.api.recipes.SuSyRecipeMaps`, so this mod keeps its *soft* dependency on SUSY and still loads fine in a pure-GT pack (a missing map only skips this pass).

Implemented by **wrapping the item handler returned from `getCapability(ITEM_HANDLER, side)`** (two mixins, because `SimpleMachineMetaTileEntity` overrides `getCapability` without calling super) rather than by hooking `insertItem` — the player GUI uses the machine's *internal* handler reference, so it naturally bypasses the wrapper. Client → server uses a small custom packet ([`PacketSetFluidCapacity`](src/main/java/com/susy/plusplus/network/PacketSetFluidCapacity.java)) instead of ModularUI synced values, because the compile-time 3.0.4 and runtime 3.1.6 APIs differ there (a `NoSuchMethodError` this project has already hit once).

Plain single-tank machines, quantum tanks and this mod's fluid sample storage also work; parts with no fluid tank (e.g. item buses) still just report "no fluid tank". Depth-limited and de-duplicated to avoid cycles. Capacities are written by reflected access to Forge's `FluidTank.capacity` with a safe fallback.

## [1.0.5] - 2026-09-30

### Fixed
- **Crash when opening any XNet GUI** (`NoClassDefFoundError: com/susy/plusplus/mixin/xnet/XNetPatchText`): the shared localisation helper had been placed inside `com.susy.plusplus.mixin` — the very package listed as `"package"` in `mixins.susyplusplus.json`, which Mixin adds to the **class-loader exclusion list**. A `@ModifyConstant` replacement is *merged into the target class* (here XNet's `GuiController`), so at runtime the reference is resolved by the ordinary class loader, which cannot see anything in the mixin package. The helper now lives in [`com.susy.plusplus.integration.xnet`](src/main/java/com/susy/plusplus/integration/xnet/XNetPatchText.java) and all 11 patched GUI classes import it. (The older patches were unaffected because they declared `localize` *inside* the mixin class, so it got merged into the target together with the handler.)
- The controller GUI's channel-type dropdown was still showing the raw key `xnet.item`: `GuiController` feeds `IChannelType#getID()` straight into a `ChoiceLabel`, and mcjtylib's widgets never call `I18n`. Fixed by adding the `xnet.item`/`xnet.energy`/`xnet.fluid`/`xnet.logic` keys *and* a `mcjtylib` mixin that localises only the **displayed** text of `AbstractLabel#setText` for strings starting with `xnet.` — the underlying value stays the raw id, so channels are still created correctly.
- Aiming at a GT machine with HoloInventory still showed `tile.unnamed`: `TileRequest` has **no getter at all** for its `pos` field, so the earlier `getMethod("getPos")` reflection threw `NoSuchMethodException`, was swallowed, and the injection returned early every time. The handler now reflects the private `pos` field (walking up the superclass chain).

### Added
- **Third-party compatibility patches** (master switch `enableThirdPartyPatches`, default on). Both are optional and **completely skipped when the target mod is absent** (`@Pseudo` on every patched mixin + a `SuMixinPlugin` gating on `Loader.isModLoaded`), so packs without those mods are unaffected:
  - **XNet localisation**: this mod now ships `assets/xnet/lang/zh_cn.lang` (XNet itself only ships de_de/ru_ru/tr_tr/en_us, so Chinese users only ever saw English). It mirrors upstream's keys/`%s`/`@f`/`@6`/`\n` exactly. This is a plain resource and is **not** affected by the config switch.
  - **XNet hardcoded strings**: the UI texts hardcoded in xnet's bytecode are replaced with localisable keys via `@ModifyConstant(method = "*", ...)` — no refmap, no dependency on xnet's internal method names. Coverage was extended from the original 3 controller messages + 8 controller errors + 3 redstone-proxy tooltips to **~90 strings across 14 target classes**: the whole controller GUI (buttons `Create`/`Paste`/`Cancel`/`OK`, labels `Channel`/`Connector:`/`Block:`/`Position:`, clipboard messages and their tooltips), the redstone-mode tooltips (`AbstractEditorPanel`), the connector GUI (`Name:`/`Directions:`), the router table headers (`Ch`/`Pos`/`Index`), and every channel/connector settings panel (item / fluid / energy / logic, including the `Pri`/`Rate`/`Min`/`Max`/`Filter`/`BL`/`Ore`/`Meta` labels and all their tooltips). GUI-command tags, NBT keys and JSON fields (`"mode"`, `"priority"`, `"flt"`, …) plus pure-symbol buttons (`x`, `C`, `?`) are deliberately left untouched. Likewise, `AbstractEditorPanel`'s redstone option names (`"Ignored"`/`"Off"`/`"On"`/`"Pulse"`) are **not** replaced even though they look localisable: they double as the *serialized value* (`redstoneMode.addChoiceEvent((parent, newChoice) -> update(tag, newChoice))` → server `RSMode.valueOf(((String) data.get(TAG_RS)).toUpperCase())`), so translating the constant would make the server throw `IllegalArgumentException` and break the setting. Only their tooltips are replaced; the visible option name is localised at the display layer instead.
  - **XNet dropdowns and generated option names**: the controller GUI's "type" dropdown (shown when creating a channel) listed the raw `IChannelType#getID()` keys (`xnet.item`, `xnet.energy`, `xnet.fluid`, `xnet.logic`), because mcjtylib's widgets never call `I18n` (verified: the whole library only references I18n in `BaseBlock`). Those keys are now added to `zh_cn.lang`, and a new `mcjtylib` mixin (`@ModifyVariable` on `AbstractLabel#setText`) localises the *displayed* text while leaving the underlying value intact — so "Create" still sends the real id and channels are built normally. The same hook also translates a strict **whitelist** of XNet's runtime-generated option names: `AbstractEditorPanel#choices(Enum...)` builds each label with `StringUtils.capitalize(enum.toString().toLowerCase())` (so `INS`→`Ins`, `PRIORITY`→`Priority`, `RND`→`Rnd`), which **no `@ModifyConstant` can ever see** because those strings only exist at runtime. Covered now: `Ins`/`Ext`, `Single`/`Stack`/`Count`, `First`/`Rnd`/`Order`, `Priority`/`Roundrobin`/`Distribute`, `Sensor`/`Output`, `Item`/`Fluid`/`Energy`/`Rs`, and `Ignored`/`Off`/`On`/`Pulse`. Anything that is neither `xnet.*` nor in the whitelist is passed through untouched (numbers, machine names and user input are never mangled), and because only the displayed text changes while `ChoiceLabel` keeps the raw value in its own `currentChoice` field, what is sent to the server is unchanged — so settings still save and no `valueOf(...)` throws.
  - **HoloInventory machine names**: aiming at a GT machine now shows the machine's real name. HoloInventory names a hologram only when the *item handler* implements its `api.INamedItemHandler` (GT predates that API), so the patch intercepts `TileRequest$Handler#onMessage` server-side, recognises GT machines via `IGregTechTileEntity`, and supplies the name (response built reflectively so HoloInventory is not a compile-time dependency). The handler reads `TileRequest`'s **private `pos` field** reflectively — the class has *no getter at all*, and the earlier attempt with `getMethod("getPos")` threw `NoSuchMethodException` that was swallowed, so the injection silently did nothing and the hologram kept showing GT's own block fallback name `tile.unnamed` (`BlockMachine` is registered with `setTranslationKey("unnamed")`).
  - Docs: [docs/third_party_patches.md](docs/third_party_patches.md).
- New config option `enableThirdPartyPatches` (default `true`).
